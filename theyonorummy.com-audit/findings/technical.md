## 1. Crawlability

**robots.txt** (`https://theyonorummy.com/robots.txt`, generated by `app/robots.js`) — confirmed live:
```
User-Agent: *
Allow: /
Disallow: /admin/
Disallow: /api/

Sitemap: https://theyonorummy.com/sitemap.xml
```
Correct and minimal. **PASS.**

**sitemap.xml** (`app/sitemap.js`) — confirmed live, 83 `<loc>` entries: 1 homepage (priority 1.0) + 9 category pages (priority 0.6: `slots`, `rummy`, `jaiho`, `vip`, `777`, `spin`, `bet`, `diwa`, `jackpots`) + 73 app detail pages (priority 0.8, real `lastModified` dates from `app.lastUpdated`). No `/admin` or `/api` URLs present. **PASS.**

- Info: 3 of the 9 sitemapped categories (`jaiho`, `bet`, `jackpots`) exist only because real apps in the DB carry those tags (unioned in via `apps.flatMap(app => app.categories)`), not because they're in `FEATURED_CATEGORIES`/`NAV_CATEGORIES` in `lib/categoryContent.js`. They render fine (verified live, 200 OK) but have no hand-written content — see Indexability §2 thin-content note below.

**Severity: High — `www.theyonorummy.com` resolves with `200 OK` instead of redirecting to the apex domain.**
Confirmed: `curl -I https://www.theyonorummy.com/` returns `200 OK` serving the identical Next.js app (same headers, same content), with no redirect to `https://theyonorummy.com/`. This creates a second fully-crawlable, fully-indexable host serving duplicate content for every URL on the site. Canonical tags do point to the apex domain everywhere (mitigates the worst outcome — Google should consolidate via canonical signal), but this is not a substitute for a real redirect: it leaves ranking-signal splitting up to Google's judgment, allows `www` backlinks/shares to dilute authority, and is trivial to fix.
**Fix:** Add a server-level 301 redirect from `www.theyonorummy.com/*` → `https://theyonorummy.com/*` at the nginx/DNS layer (the app is served via nginx per the `Server: nginx/1.24.0 (Ubuntu)` header, so this belongs in the nginx vhost config, not `next.config.mjs`). Do this **before** Search Console submission — set up both the apex and `www` properties in GSC afterward regardless, so any residual `www` signals are visible.

**Severity: Info — HTTP → HTTPS redirect confirmed correct.** `curl -I http://theyonorummy.com/` → `301` → `https://theyonorummy.com/`. **PASS.**

**Severity: Info — trailing-slash normalization confirmed correct.** `/category/rummy/` → `308` → `/category/rummy` (Next.js default `trailingSlash: false` behavior, single-hop, no chain). **PASS.**

**Severity: Info — case sensitivity confirmed safe.** `/Category/Rummy` and `/CATEGORY/RUMMY` both return a clean `404` (no case-insensitive duplicate URLs being served as 200). **PASS.**

**Severity: Medium/Low — IndexNow protocol not implemented.** No `/indexnow-key.txt` (or similarly named key file) found (`404`), and nothing in the codebase pings Bing/Yandex/Naver's IndexNow endpoint on publish/update. Since this site updates app listings and bonus amounts "daily" per its own sitemap `changefreq`, and is about to be submitted fresh, IndexNow is a cheap way to get faster indexing/re-indexing on Bing (and Yandex/Naver, less relevant for an India-focused audience but free either way) without waiting on their crawl schedule.
**Fix:** Generate a key, host it at `/{key}.txt` (a static file in `public/` works), and call the IndexNow API (`https://api.indexnow.org/indexnow`) whenever an app is added/edited/deactivated in the admin panel (`app/admin/actions.js` is the natural integration point) and whenever `sitemap.js`'s underlying data changes.

## 2. Indexability

**Canonical tags** — confirmed correct and present on every page type checked:
- Homepage: `<link rel="canonical" href="https://theyonorummy.com"/>`
- Category pages: self-referencing, e.g. `https://theyonorummy.com/category/rummy`
- App detail pages: self-referencing, e.g. `https://theyonorummy.com/max-rummy`

**PASS.**

**Meta robots on filtered/search views** — confirmed correct (`app/page.js` `generateMetadata`):
- `/?q=<term>` → `robots: { index: false, follow: true }`, canonical → `https://theyonorummy.com`
- `/?category=<slug>` → `robots: { index: false, follow: true }`, canonical → `https://theyonorummy.com/category/<slug>`

This is genuinely above-average handling — most directory sites either let every query-string permutation get indexed or block search entirely with `disallow`. Here, Googlebot can still crawl and pass link equity through, but won't index the near-duplicate parameterized URL. **PASS.**

**Severity: High — homepage vs. `/category/rummy` keyword cannibalization risk.**
- Homepage: `<title>Yono Rummy Games 2026 | All Yono Games List</title>`, H1 "Yono Rummy Games - All Yono Games 2026", and its two largest body-copy blocks ("Yono Rummy Games & All Yono Games List 2026", "How much bonus do Yono Rummy games offer?") are Rummy-first, generic-directory-second.
- `/category/rummy`: `<title>Yono Rummy - All Yono Rummy Games List & APK Download</title>`, H1 "Yono Rummy: All Yono Rummy Games List & APK Download 2026", with dedicated Rummy-only sections ("What are Yono Rummy games?", "Bonus and withdrawal in Yono Rummy apps," etc.).

Both pages are optimizing for essentially the same head term ("yono rummy [games]"), with overlapping title patterns, overlapping H1 wording, and overlapping body themes (bonus range ₹51–₹500, ₹100 min withdrawal, install-from-unknown-sources steps — near-identical phrasing appears on both). This is a real cannibalization risk: Google may pick one of the two to rank and suppress the other, and internal linking/anchor-text signals are currently split between them since the homepage nav, category pills, and the rummy category page all reinforce "Yono Rummy" as the primary entity for both URLs.
**Fix (pick one strategy, don't leave it ambiguous):**
1. **Differentiate the homepage's positioning** — reposition its title/H1/intro copy toward the umbrella brand ("All Yono Games — Rummy, Slots, 777 & More Apps List") rather than leading with "Rummy," and let `/category/rummy` own the rummy-specific query. This is the lower-risk option since it doesn't touch a page that's about to accumulate the most backlinks/authority as the primary landing page.
2. Alternatively, if "yono rummy" (not "yono games") is genuinely the primary target keyword/brand term the business wants the **homepage** to rank for, then de-emphasize rummy-specific long-form content on `/category/rummy` and lean it harder into being a pure listing/filter page, with the deep "what is Yono Rummy" educational content living only on the homepage.
Either way, monitor both URLs' rankings for "yono rummy" once Search Console has data (Performance report, filter by query, check which URL Google is actually serving) and adjust.

**Severity: Medium — thin/templated content on non-featured category pages.**
`/category/jaiho`, `/category/bet`, `/category/jackpots` (and any other category that exists only because an app happens to carry that tag, not because it's in `lib/categoryContent.js`'s `categoryContent` object) render with just the hero heading/subheading (generic template string: `` `Verified Yono ${label} apps with signup bonuses from ₹51 to ₹500 and safe, tracked referral links.` ``) and the app grid — no unique body sections, versus the 4 unique H3/body sections that `slots`/`rummy`/`777`/`vip`/`spin`/`diwa` get. Confirmed live: `/category/jaiho` is 54KB HTML vs. `/category/rummy` at 199KB, most of that gap being the missing content sections (`content?.sections?.length > 0` gate in `app/category/[category]/page.js` simply renders nothing when `getCategoryContent()` returns `null`). These pages are still legitimately indexable (they have a real, unique app grid + unique meta title/description generated from the template), but their generic hero copy is templated across categories and offers little differentiation for Google or users.
**Fix:** Either add a `categoryContent` entry for every category that actually has apps tagged against it (check via `App.distinct('categories', {isActive:true})`), or, if a category is minor/low-volume, consider `noindex,follow`-ing it until it has enough apps/content to justify a dedicated page, or folding it into a related featured category instead of giving it its own thin URL.

**Structured data** — confirmed via live JSON-LD extraction, valid `@graph` present on every page type: `Organization`, `WebSite` (+ `SearchAction` sitelinks-search-box target), `CollectionPage`, `ItemList`/`ListItem`, `BreadcrumbList` (category/app pages), `SoftwareApplication` (app pages, with `operatingSystem`, `applicationCategory: GameApplication`, `offers`). Breadcrumb correctly omits the non-navigable "Categories" middle crumb from JSON-LD (it's shown visually but excluded from schema since Google requires a real `item` URL on every non-terminal node) — a subtle detail done right. **PASS**, see §7 for one enhancement opportunity.

**404 handling** — confirmed correct: unknown slugs return true HTTP `404` + `<meta name="robots" content="noindex"/>`, served from Next.js's prerendered not-found page (`x-nextjs-prerender: 1`). **PASS.**

**Admin surface** — `/admin/login` returns `200` (login form is meant to be publicly reachable) but carries `<meta name="robots" content="noindex, nofollow"/>`, and `/admin` itself 307-redirects to `/admin/login` via `middleware.js`'s session-cookie check. Combined with the `robots.txt` disallow on `/admin/`, this is defense-in-depth. **Info-level nuance worth knowing:** because `robots.txt` disallows `/admin/`, Googlebot will never actually fetch `/admin/login` to see the `noindex` tag — the disallow alone is what's preventing crawling; the `noindex` only helps in the edge case where the URL gets indexed anyway from an external link with no crawl (URL-only indexing). This is a reasonable belt-and-suspenders setup for a low-risk internal page and not something to change now, just worth understanding rather than assuming both mechanisms are independently doing full work here.

## 3. Security

**Severity: High — no security headers on any response.** Confirmed via header dump across homepage, category pages, app detail pages, and the custom 404 — identical gap on every page type:

| Header | Status |
|---|---|
| `Content-Security-Policy` | **Missing** |
| `Strict-Transport-Security` (HSTS) | **Missing** |
| `X-Frame-Options` | **Missing** |
| `X-Content-Type-Options` | **Missing** |
| `Referrer-Policy` | **Missing** |
| `Permissions-Policy` | **Missing** |
| `X-Powered-By` | **Present and exposing `Next.js`** (should be suppressed) |

`next.config.mjs` currently exports an empty config (`const nextConfig = {}; export default nextConfig;`) — no `headers()` function, no `poweredByHeader: false`. There's no CDN/WAF in front of origin either (`Server: nginx/1.24.0 (Ubuntu)` responds directly), so nothing upstream is adding these headers either.

Why this matters specifically for this site: it's a real-money-gaming referral property that will run affiliate/download links and (eventually) an admin panel with authentication cookies — the exact profile where clickjacking (missing `X-Frame-Options`/CSP `frame-ancestors`), MIME-sniffing (`X-Content-Type-Options`), and protocol-downgrade/cookie-theft (missing HSTS) protections matter most, and where their absence is easy for a competitor, security researcher, or user to notice and flag.

**Fix — add to `next.config.mjs`:**
```js
/** @type {import('next').NextConfig} */
const nextConfig = {
  poweredByHeader: false,
  async headers() {
    return [
      {
        source: '/:path*',
        headers: [
          { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains; preload' },
          { key: 'X-Frame-Options', value: 'SAMEORIGIN' },
          { key: 'X-Content-Type-Options', value: 'nosniff' },
          { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
          { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
          // Start Content-Security-Policy in report-only mode first — this app uses
          // next/image, next/font, and inline JSON-LD <script type="application/ld+json">
          // tags (app/page.js, app/category/[category]/page.js, app/[slug]/page.js all use
          // dangerouslySetInnerHTML for JSON-LD), so a naive CSP will break those unless
          // 'unsafe-inline' or a nonce/hash strategy is used for those specific scripts.
        ],
      },
    ];
  },
};
export default nextConfig;
```
Roll out HSTS and the other headers immediately (low risk, no app-code dependency). Roll out CSP in `Content-Security-Policy-Report-Only` mode first and tighten it over 1–2 weeks once you've confirmed the JSON-LD inline scripts and any third-party embeds (Telegram link, ad network scripts if/when added) don't get blocked — don't ship a blocking CSP untested on a site that hasn't launched yet, since the inline JSON-LD `<script>` tags on every page will need either `'unsafe-inline'` or nonces to survive it.

**SSL/TLS** — confirmed: valid Let's Encrypt certificate (`CN=theyonorummy.com`, issued by `Let's Encrypt R-series CA`), valid window `2026-07-16` to `2026-10-14` (~90-day LE cert, standard), TLS 1.2 and TLS 1.3 both negotiate successfully with modern ciphers (`ECDHE-ECDSA-AES256-GCM-SHA384` / `TLS_AES_256_GCM_SHA384`). **PASS** — just confirm the LE renewal automation (certbot cron/systemd timer) is actually active on the server, since this is a manually-managed nginx box, not a platform that auto-renews for you.

## 4. URL Structure

Clean, flat, human-readable URLs throughout: `/max-rummy`, `/category/rummy`, no query-string-based routing for canonical content, no session IDs or tracking params in indexable URLs. **PASS.**

See §1 for the **www → apex redirect gap (High)** — repeated here because it's as much a URL-structure issue as a crawlability one.

**Severity: Low/Medium — outbound download/affiliate links aren't marked `rel="nofollow sponsored"`.**
Every "Download" CTA (`AppCard.js`, `app/[slug]/page.js`) points to `/api/download/{slug}`, an internal Next.js route (`app/api/download/[slug]/route.js`) that looks up `app.referLink` in MongoDB and issues a `302` redirect to the real (external, presumably paid/affiliate) destination — with a nice touch: it explicitly checks `User-Agent` for `Googlebot|AdsBot-Google` and redirects those to the homepage instead, so Googlebot never even follows the real referral link. Combined with `/api/` being disallowed in `robots.txt`, Googlebot cannot crawl this redirect chain at all today, which is a legitimate and reasonably clever way to keep the internal-to-external hop invisible to crawlers.

That said, the visible anchor/CTA elements linking to `/api/download/{slug}` don't carry `rel="nofollow"` or `rel="sponsored"` themselves. Since `robots.txt` already blocks the URL from being crawled, this isn't currently causing PageRank to flow anywhere problematic — but it's worth adding anyway as defense-in-depth and because Google's own guidance is to mark the anchor itself, not rely solely on a crawl block, especially for what is functionally a paid/affiliate link on a monetized directory. It also protects you if `/api/` is ever accidentally un-blocked in a future robots.txt edit.
**Fix:** add `rel="nofollow sponsored"` to the download CTA `<a>` tags in `components/AppCard.js` and `app/[slug]/page.js`.

**Redirect chains** — none found beyond the single expected hops (`http→https`, trailing-slash strip). **PASS.**

## 6. Core Web Vitals

**Important caveat before the specifics:** this is a pre-launch site with no real users yet, so there is no CrUX field data, and there won't be any in Search Console/PageSpeed Insights until it accumulates ~28 days of real Chrome traffic post-launch. The automated PSI check attempted for this audit (`theyonorummy.com-audit/_ps_home.json`) hit a rate limit (`"PSI rate limit exceeded (240 QPM / 25,000 QPD)"`) before it could return lab data, and a separate raw-fetch attempt (`_render_home.json`) timed out — both are pre-existing empty artifacts, not something this audit could regenerate in-session. **Recommend re-running PageSpeed Insights (mobile + desktop) and/or Lighthouse-in-Chrome-DevTools against the live URL manually before submitting to Search Console**, ideally from a location/network close to the target audience (India, mixed 4G/budget-Android). Everything below is inferred from response headers, HTML payload inspection, and manual `curl` timing — treat it as a prioritized checklist for that Lighthouse run, not as lab-equivalent numbers.

**Severity: Medium/High — homepage is fully dynamic and uncached on every request.**
Confirmed via headers: homepage returns `Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` with no `x-nextjs-cache` header at all, meaning every single request — including every Googlebot crawl — triggers a fresh `dbConnect()` + `App.find()` + `App.distinct()` round trip to MongoDB, live, with no ISR/static caching layer. This is expected/necessary for the `?q=` and `?category=` search-parameter variants (Next.js correctly forces dynamic rendering wherever `searchParams` is read), but it also applies to the plain `/` homepage with zero params — the single highest-priority URL in the sitemap (`priority: 1`) and the one most likely to get the most crawl and user traffic. By contrast, `/category/*` and `/[slug]` pages **are** properly build-time/ISR-prerendered (confirmed: `x-nextjs-cache: HIT`, `x-nextjs-prerender: 1`, `Cache-Control: s-maxage=31536000` on both `/category/rummy` and `/max-rummy`) — so this is specifically a homepage gap, not a site-wide pattern.
Manual TTFB sampling (3 repeat requests) showed `1.17s–3.34s` for `/`, versus `0.81s–1.26s` for a cached app page and `~1.1s` for a static image asset served directly by nginx — i.e. even the network-latency floor from this test environment to the origin is high (~1.1s, likely reflecting this environment's distance from the server rather than the server itself), but the homepage consistently adds real additional time on top of that floor that the cached pages don't. This is worth fixing regardless of the absolute numbers' confounded-by-network-path caveat.
**Fix:** Cache the unfiltered (`!q && !categoryFilter`) query path — e.g. wrap the `App.find()`/`App.distinct()` calls for the default view in `unstable_cache` with a short revalidate window (e.g. 5–10 minutes, matching how often the admin panel actually publishes changes), while leaving the `?q=`/`?category=` dynamic paths as they are today.

**Severity: Medium — homepage renders all ~74 apps in one ungated grid, no pagination.**
Confirmed: homepage HTML is 339KB raw (gzipped transfer ~20KB, so compression is doing real work, but the DOM itself and the embedded RSC/flight-data payload used for hydration are both sized to every app in the DB at once — 73 app entries were present in the live sitemap at audit time, and this will only grow). No pagination, "load more," or virtualization exists in `app/page.js`. On a directory site whose target audience skews toward budget Android devices on Indian mobile networks, a large unpaginated DOM plus a proportionally large hydration payload is a plausible INP and mobile-CPU-parse-time risk as the app catalog keeps growing (currently ~74 apps; the risk compounds directly with catalog size).
**Fix:** Add pagination or a "show N, load more" pattern to the homepage grid once the catalog is large enough to matter (74 is already a reasonable trigger point) — category pages will face the same issue individually as they grow and should get the same treatment.

**Severity: Low — `next/image` used with `unoptimized` everywhere.**
Every `<Image>` usage (`AppCard.js`, `app/[slug]/page.js`, `app/page.js`'s popular-games strip) sets `unoptimized`, which skips Next.js's automatic AVIF/WebP negotiation, resizing, and responsive `srcset` generation, serving the source file as-is. In this case the impact is small because the source app-logo images are already pre-optimized `.webp` files served from `/icons/` (confirmed: `max-rummy.webp` is 9.2KB, `image/webp`), so you're not shipping unnecessarily large images today — but you're also not getting responsive sizing (a 512×512 logo gets shipped even where it renders at 70px), and if a future admin upload adds a large unoptimized image, there's no automatic safety net. Likely reason for `unoptimized` is that `next.config.mjs` has no `images.remotePatterns`/`domains` configured, so any externally-hosted logo would otherwise 400 at the image-optimization endpoint.
**Fix (optional, not urgent):** if all app logos are self-hosted under `/icons/` or `/public`, remove `unoptimized` and let `next/image` generate responsive variants; if logos can come from arbitrary external URLs via the admin panel, configure `images.remotePatterns` for the specific allowed hosts instead of disabling optimization globally.

**Severity: Low — inconsistent/weak cache headers on static assets.**
`/logo.webp` (served from `public/`) returns `Cache-Control: public, max-age=0` (effectively no caching) while `/icons/max-rummy.webp` returns `public, max-age=3600` (1 hour) — both are fully static, rarely-changing image assets that should be cacheable far longer. Compare to the Next.js build assets (`/_next/static/css/*`, `/_next/static/chunks/*`), which correctly return `public, max-age=31536000, immutable` since they're content-hashed.
**Fix:** Add a long `max-age` + `immutable` (or content-hash the filenames) for `public/` static assets via nginx or a `headers()` rule in `next.config.mjs`, matching what `_next/static` already gets.

**Severity: Info — no CDN in front of origin.** `Server: nginx/1.24.0 (Ubuntu)` responds directly with no CDN/edge-cache signature (no `cf-ray`, no `x-vercel-id`, etc.). The `s-maxage=31536000` cache-control hints Next.js is already emitting on ISR-cached pages are meant for a shared/edge cache — without one in front of origin, those hints are currently doing nothing, and every request (cached or not) still makes a round trip to the single origin server, which is also a single point of failure/latency for all Indian mobile users regardless of where the server itself is hosted. **Recommend fronting the site with a CDN** (Cloudflare or similar) both to actually use the caching hints already being emitted and to get edge presence closer to the target audience — this would also incidentally provide an easy path to add most of the missing security headers in §3 at the edge if that's easier than touching the nginx config directly.

**Positive findings for CWV:**
- gzip compression confirmed enabled (`Content-Encoding: gzip`) on HTML responses. **PASS.**
- `font-display: swap` + metric-matched fallback fonts — low CLS risk from web fonts (see §5). **PASS.**
- Image containers use explicit `aspect-square`/fixed-dimension wrappers (`AppCard.js`, homepage popular-games grid, app detail logo) rather than unconstrained `<img>` tags, which is the correct pattern to prevent image-driven CLS regardless of the `unoptimized` note above. **PASS.**
- `/category/*` and `/[slug]` routes are properly statically prerendered with a 1-year `s-maxage`, confirmed via `x-nextjs-cache: HIT` — this is the majority of the site's pages (73 of ~83 sitemap URLs) already doing the right thing. **PASS.**

## 7. Structured Data

Valid `@graph`-based JSON-LD confirmed live on every page type (see §2). One enhancement opportunity:

**Severity: Medium (opportunity, not a defect) — `SoftwareApplication` schema omits `aggregateRating`.**
`app/[slug]/page.js`'s `softwareApplicationNode` includes `name`, `operatingSystem`, `applicationCategory`, `url`, `image`, `description`, and `offers`, but not `aggregateRating` — despite `app.rating` and `app.ratingCount` being real fields in the `App` model (`models/App.js`) that are already rendered visibly on-page via `StarRating`/the rating number. Adding `aggregateRating` would make these pages eligible for star-rating rich results in search, which meaningfully helps CTR on directory/comparison listings.
The prior internal audit (`SEO-AUDIT-REPORT.md`) explicitly called out avoiding "fabricated review-count schema" as a strength — that caution is correct and should stay in place if `rating`/`ratingCount` are ever seeded/placeholder values rather than genuine user data. **Only add `aggregateRating` if the underlying rating/count numbers are genuinely sourced** (real user reviews, or a transparently-disclosed editorial rating methodology) — Google's structured data policies explicitly prohibit schema that doesn't reflect genuine ratings, and this is a YMYL-adjacent (real-money gambling) niche where a manual action for spammy structured data would be a costly mistake. Verify the data provenance with whoever populates `rating`/`ratingCount` in the admin panel before implementing.

No other structured data issues found — `BreadcrumbList` correctly omits non-navigable intermediate nodes, `WebSite`/`SearchAction` sitelinks-search-box markup is correctly formed, `Organization`/`CollectionPage` nodes are well-formed.
